### Phase 26 — Pre-launch functional audit + remediation (2026-08-11, on `main`)
A full role-by-role audit of the system before it goes live for real staff and real payroll, followed by fixes. Discovery ran first with no fixes; every finding below was reproduced over live HTTP with real login sessions before it was touched, and every fix re-verified the same way. Commits so far:

- **Points integrity (`bbf2e79`)** — unbounded point awards on review/PATCH, soft-deleted tasks still inflating scores and balances, `DELETE /requests` not gated to Admin.
- **Lead scoping (`1cea930`)** — two competing "can this Lead see this employee?" implementations existed. The `viewer.teamId === target.teamId` one made a Lead's **second team invisible to its own Lead**, which is why `task-activity` returned 200 while `employees/:id` returned 403 for the same person. Everything now resolves through `lib/employees/managed-scope` (`getLedEmployeeIds` / new `leadsEmployee`). Two adjacent defects fell out of the same sweep: announcements picked one led team arbitrarily via `findFirst`, and `GET /attendance` silently widened an out-of-scope `employee_id` filter back to "my whole team", labelling someone else's attendance as the requested person's. Verified: 8 endpoints 200 for the owning multi-team Lead (3 were 403), negative control 403/empty throughout.
- **Attendance classification (`448118d`)** — three defects that all moved real money. Days **before an employee joined** counted as absences, deducting a full month from a new hire's first payslip; a **sub-1.5h day was paid as a full day** (the old floor's other half was never implemented, so a five-minute day out-earned a four-hour one); a **zero-hour record was paid as a full day**. `dayCredit()` is now the single decision point, and `todayDateOnly()` no longer returns yesterday for the whole 00:00–05:30 window in IST. The half-day policy call — a short day is worth half, never zero, for someone who turned up — is a deliberate employee-favourable reading of an open question, reversible in one place.
- **Re-clock-in + sessions + work-from-home (this commit)** — owner ask, verbatim: *"employee should be able to clock in but not log progress without clocking in again."* Clocking out used to be terminal: an employee who stepped out at lunch was locked out of their own day. The single `clock_in_raw`/`clock_out_raw` pair could not express this — overwriting `clock_in_raw` destroys the day's first-in that late-arrival depends on, and leaving it alone pays the break as work. So a day is now one record **plus one or more `attendance_sessions`**: `clock_in_raw`/`clock_out_raw` are the day's bounds, and `total_hours` is the **sum of closed sessions**. This is also exactly the shape the TeamOffice biometric feed needs (every punch opens or closes a session), so it is built once rather than twice.
  - Clock-in opens a session and 409s only if one is already open — or if the day is already **approved**, since reopening it would silently invalidate approved times payroll has already read. Re-clock-in reopens the day (`clock_out_raw`/`total_hours` → `null`) and skips the "pick a task" requirement, which belongs to the day's first clock-in; re-planning after lunch is friction, not discipline.
  - Clock-out takes `{ endOfDay?: boolean }` (default `true`, so a bare POST is unchanged). `false` = stepping out: it closes the session but fires **no** EOD wrap-up to the employee or report to management — otherwise every lunch break would page Admin/HR.
  - **The gate the owner asked for:** `isClockedInNow` now means *an open session right now*, so completing a task or self-logging is blocked while clocked out, while clocking back in is always allowed.
  - **Work-from-home clock-in is now built** (it did not exist before — the pre-existing `RequestType.wfh` is the ask-permission-ahead flow, a different thing). `work_location` (`office` | `wfh`) is chosen at clock-in, stored per session, and copied to the record from the day's first session. A WFH day is a normally worked, normally paid day.
  - Cascaded to: `attendance/[id]/edit` and `.../approve` (recompute from sessions unless Admin/HR explicitly set approved times, which win), the EOD cleanup cron (closes open **sessions**, defaulting each from its *own* start so a 16:00 return isn't credited from the morning), `GET /attendance` (returns `sessions`), the `useAttendanceStatus` hook, the home ClockCard (total-today vs current-session are now genuinely different numbers), Daily Planning (WFH radio, "Step out (break)" vs "Clock out & generate EOD", "Clock back in") and My Tasks.
  - Migration `20260811141041_attendance_sessions_and_work_location` **backfills one session per existing record** — without it every already-recorded day would sum to zero hours and every open day would read as "not clocked in".
  - **Verified:** typecheck exit 0; 179 unit tests pass (up from 168) including a new `lib/attendance/sessions.test.ts` proving a two-session day with a two-hour gap is worth 7h, not 9h; **11/11 live HTTP checks** as a real employee — WFH clock-in, double clock-in still 409, progress allowed while in, break, progress **blocked** while out (422 "You must be clocked in"), clock back in **201 where it was 409 before**, `clock_in_raw` unmoved at the day's first punch, and final worked time strictly less than the day's span. One sub-check ("completing a task is blocked while clocked out") was **skipped** — the seeded employee has no atomic task assigned; the same guard was proven through the self-log route. All test rows deleted, zero remaining verified.

- **Malformed input returned 500 on 22 endpoints (this commit)** — probed, not guessed: `GET /employees/not-a-uuid` and 21 siblings answered a bare, envelope-less **500**, because every `:id` is a Postgres `uuid` and a non-UUID string makes Prisma throw P2023 rather than return no rows. ### Phase 25 — Self-logged ad-hoc tasks (2026-08-10, on `main`)
Owner ask, verbatim: *"also for the tech employees If no tasks assigned, employees can log new tasks themselves while clock in or during the day, but need to figure out the point system for that."* The point system was the actual problem; the rest follows from it.

- **The point system, and why it looks like this: nobody judges difficulty.** An employee estimating their own points is marking their own exam, and a Lead estimating them is a technical judgement a non-technical Lead cannot make. So the employee picks a **type** from a fixed Admin-set catalog (`adhoc_task_types`, seeded: bug fix 2, small feature 3, large feature 8, support 2, chore 1, documentation 1, research 3) and the Lead answers exactly one question at review — *did this happen, yes or no*. Anyone can answer that.
- **`POST /work-items/self-log`** — strict zod body (`typeKey`, `title`, `description?`), so a client-supplied `points` is rejected outright rather than ignored. `taskPoints` is copied server-side from the catalog row. Must be **clocked in** (same rule as completing a task: you log work while you are at work, and it keeps the logged date honest). The department check runs *before* the clocked-in check on purpose — "you have no department" is a permanent answer about who the feature is for, and leading with the transient one would tell an Admin to clock in for a feature that would refuse them anyway. Audited (`work_item.self_log`). `GET` on the same path returns the caller's own last 50. `GET /adhoc-task-types` exposes the catalog (active-only; `?includeInactive=1` for Admin/HR).
- **Always reviewed, whatever it is worth.** `requiresReviewForItem()` in `lib/work/review.ts` overrides the point threshold for self-logged items — the tiered threshold exists to spare a Lead from rubber-stamping small *assigned* work, but here the review is the only check that the work happened at all. The review route also **422s if a Lead sends `points`** for a self-logged item: re-pricing would smuggle difficulty-judgement back in through the review screen, which is exactly what the catalog exists to avoid.
- **Container:** the same pattern as the sales provisioner — a per-department auto-created "Ad-hoc Work" → "Self-logged Tasks" WorkUnit/SubUnit, because `WorkItem.subUnitId` is non-null and a rival "loose tasks" concept would fork every downstream reader. Here the project lead genuinely matters (it is who gets the review notification), so a real Lead is preferred with the first active member only as a lead-less fallback.
- **The cap is not enforced at approval.** `cappedSelfLoggedPoints()` + `monthlyPointSplit()` (unit-tested) limit self-logged points to a share of the month's *total* credited points (`performance_config.self_logged_cap_percent`, default 30) — but at **scoring** time, not approval. Refusing to accept work that genuinely happened would be a lie about the work and the Lead would have nothing to act on. Note the floor case: with zero assigned points the cap is zero, so a month of pure ad-hoc work scores nothing. That is the intended reading — ad-hoc logging supplements assigned work rather than replacing it — and is part of why `scoring_enabled` starts off. **These helpers were not yet called by `monthly-score.ts`** at the time of this phase — wired in the Phase 26 Pillar 6 rewire (2026-08-11).
- **UI:** a "Log a task" card at the top of `/my-tasks`, disabled while clocked out, hidden entirely when the catalog is empty. Options read `{label} — {points} pts`, so the price is visible before choosing, and the copy says plainly that the lead confirms it before the points count.
- **Verified:** `bun test lib/work/` 17 pass / 0 fail; typecheck clean; **29 live HTTP checks, 0 failed** with real login sessions — catalog RBAC (anon 401, active-only), clocked-out 422, unknown type 422, client-supplied points 422, short title 422, points come from the catalog, item is `selfLogged`/`pending`/due today, appears in My Tasks, goes to `in_review` despite being *below* the threshold, no points until acceptance, Lead re-price 422, unrelated lead 403, acceptance credits exactly the type's points, Admin 403, both audit rows present. Real Chromium screenshot of the card reviewed. All test rows (self-logged items, ledger rows, the auto-created container, the attendance record and its daily selections) deleted afterwards — verified zero self-logged items and zero "Ad-hoc Work" units remaining.
- **Still open (at the time of this phase):** the Pillar 6 rewire (department-aware weights, `scoring_enabled` gating, applying the self-logged cap in the output component, and `monthly-score.ts:130` scoring a `targetValue = 0` item as 0% rather than unmeasurable) — **done in Phase 26 (2026-08-11)** — and Admin settings UI/APIs for `sales_target_config` / `performance_config` / `adhoc_task_types`, still open.

### Phase 24 — "Make it a daily task until undone" — the toggle, end to end (2026-08-10, on `main`)
Phase 22 added `work_items.repeat_daily` and taught the rollover cron to honour it, but nothing outside the sales auto-provisioner could ever set it. Owner ask, verbatim: *"for the other departments also like bde when any task is added give option to make it a daily task until undone."* This closes that loop.

- **Create:** `POST /sub-units/:id/work-items` accepts `repeatDaily?`. **Atomic-only** — a daily-frequency metric item already rolls forward by construction, so accepting the flag there would offer a switch that changes nothing. A recurring task with no due date is given today's, matching what the cron stamps on every later instance; otherwise instance one carries a date its own clones don't and reads as the odd one out.
- **Undo:** `PATCH /work-items/:id` accepts `repeatDaily` as a **management-only** field (same guard as title/points/assignee — an assignee gets 403), and 422s on a metric item. Clearing it on the *newest* instance is the whole cancel mechanism: the cron reads the flag, so there is nothing else to switch off, and older instances keep their own history.
- **UI (`work-unit-detail-screen.tsx`):** a "Repeat daily" checkbox in the atomic branch of the create form (with the one-line explanation of how to stop it), the same checkbox inline in the Lead's edit row, and a `· repeats daily` marker on the task line so it's visible without opening anything. The create-form checkbox resets after each submit — a stuck box would quietly clone chores nobody asked for.

### Phase 23 — Task-generation & performance overhaul, Pillar 5: sales dashboard (2026-08-10, on `main`)
The read side of Phase 22, built as the sales counterpart to `GET /attendance/task-progress` + `TeamTaskProgressPanel`, with the same RBAC shape.

- **`GET /sales/team-progress?date=`** → per-rep today's calls (split `crm` / `offline` / `total`) against the daily target, plus this month's site visits and bookings against a **pro-rated** monthly target, with team totals and an `unmatchedCrmRows` count. Admin/HR see everyone; a Lead sees their led teams + self (`getLedEmployeeIds`); a rep sees only their own row.
- **Pacing is the thing that makes it honest.** Monthly targets are *not* `target ÷ days in month`. They are pro-rated against the days a rep was actually expected to be selling — weekly offs (including a `WeeklyOffMove`), public holidays and approved leave all come out, reusing the existing `isOffDay` / `classifyMonth` machinery rather than reimplementing it. ### Phase 22 — Task-generation & performance overhaul, Pillar 4: CRM sales-activity sync (2026-08-10, on `main`)
Unblocks the two pillars deferred in Phase 21. Problem it fixes: a sales rep's real output (calls, site visits, bookings) lived only in the CRM, so HRM scored the sales side on hand-entered metric tasks nobody kept current — and reps had to pick a task at clock-in that was the same task every single day.

- **The whole feature, in one line:** an hourly cron pulls the CRM's per-rep daily activity, stores it in `sales_activity_sync`, and **writes through into ordinary `WorkItem.currentValue`** — there is deliberately **no parallel code path**, so progress bars, the composite score and the team dashboard all read a CRM number exactly as they read a hand-entered one.
- **Auto-provisioned targets (owner request).** Every active sales rep gets today's "Calls" daily metric item and this month's "Site visits" / "Bookings confirmed" monthly items created for them, at their resolved target — so no rep picks a task and no Lead seeds the chain. Config is versioned (`sales_target_config`, keyed by `effective_from`, defaults 100 calls/day, 20 site visits/month, 2 bookings/month) with an optional **per-employee override** on `employees` that wins over the config. `WorkItem.subUnitId` is non-null, so each sales department gets one auto-created container WorkUnit/SubUnit ("Sales Activity" → "Daily Targets") for these to hang off, rather than inventing a rival "targets" concept outside the WorkUnit tree.
- **Employee matching never guesses.** Email first (case-insensitive), then an exact case-insensitive/whitespace-collapsed `fullName` match, and **only when it is unique**. Anything else is stored with `match_method = unmatched`, `employee_id NULL`, WARN-logged via `createLogger("crm-sync")`, and surfaced as a red badge on the dashboard. Names are never reordered or fuzzy-matched — a miss is safe and visible; a misattribution is silent and wrong. Every sync re-resolves the match, so fixing a rep's CRM email retroactively attaches their history.
- **Offline calls — the open product decision, now decided (owner sign-off).** Reps working a raw Excel list make calls the CRM never sees. Mechanism: **the rep proposes, the Lead approves.** A claim is worth exactly zero until approved; self-approval is refused **even for an Admin** claiming for themselves; a decline requires a written reason; claims are capped at 500 calls/day in aggregate (so many small claims can't sidestep it) and cannot be filed for a future date or more than 14 days back. Both create and review are audited (`sales.offline_claim_create` / `_approve` / `_reject`). The dashboard always shows the split ("62 CRM + 38 offline") rather than one blended number — showing the seam is what keeps it honest.
- **Idempotency.** The day's call total is **recomputed** (CRM calls + approved offline claims), never incremented, so a re-sync, a late CRM correction, and a claim approved days after the fact all converge on the same number.
- **Schema (migration `20260810100000_add_sales_activity_and_adhoc_tasks`, purely additive):** new `sales_activity_sync`, `offline_activity_claims`, `sales_target_config`, `performance_config`, `adhoc_task_types`; new enums `SalesMetric` / `SalesMatchMethod` / `OfflineClaimStatus`; `work_items` gains `sales_metric`, `repeat_daily`, `self_logged`, `adhoc_type_id`; `employees` gains `daily_call_target`, `monthly_site_visit_target`, `monthly_booking_target`.

Replaced with a three-way `SalesMetric` enum, because the owner weights site visits and bookings *differently from each other* (17 vs 23 points) — a two-way bucket cannot express that. The activity/outcome tier is still derivable from the metric.
- **Recurring tasks (owner request, applies beyond sales).** `WorkItem.repeatDaily` makes any task — atomic or metric — regenerate each morning until it's turned off. `lib/cron/metric-daily-rollover.ts` (which the plan never mentioned; it already existed) was extended to clone `repeatDaily` **atomic** items too, and its dedupe key now includes `salesMetric` so several CRM-fed daily metrics don't collapse into one row.

### Phase 21 — Task-generation & performance overhaul, Pillar 6: composite monthly performance score (2026-08-08, on `main`)
Last of the six pillars to be built this round (Pillars 4/5 — Sales/BD CRM sync — are skipped for now: the CRM endpoint at `crm.pikoruarealty.com` is confirmed **requested but still being built**, so there is nothing to sync against yet). Problem it fixes: the recognition leaderboard's monthly score was a single raw signal (Tech = summed task points, Sales/BD = average metric attainment) that ignored everything else the system now knows — attendance, whether work landed on time, whether commitments were kept, and (since Pillar 3) a Lead's own read on quality.
- **The whole feature, in one line:** `monthly` `recognition_snapshots.score` is now a 0–100 **weighted composite** of five components — output (40%), quality (20%), attendance (20%), timeliness (10%), commitments kept (10%) — plus an inert `salesOutcome` slot at **weight 0**, reserved for CRM deal-outcome data once Pillars 4/5 land. `weekly` snapshots are untouched (still raw points/attainment) — a week is too short a window for a monthly quality rating or attendance percentage to mean anything.
- **A component with no data is *unavailable*, not zero.** Unavailable components are dropped and the remaining weights renormalise over what's left (so weights always total 100 across whatever *did* get measured). This matters concretely: a first-month hire has no Lead review yet, and scoring that gap as 0/100 would punish them for something outside their control — instead their score is 100% output+attendance+timeliness until a review exists.
- **Two judgment calls, surfaced rather than shipped silently (both confirmed with the owner before writing code):**
  1. **The plan's suggested RBAC narrowing of `GET /recognition` (any authenticated user → self + owning Lead + Admin/HR) was explicitly declined.** The leaderboard stays public for everyone, as it already was — component breakdowns (including the attendance % and the numeric quality rating, never the review's written note) are visible on every row to any authenticated user, same as the score always was.
  2. **Commitment adherence deviates from the plan's literal "same-day" `DailyTaskSelection`↔`WorkItem.completedAt` join.** That definition would score a well-run multi-day task as mostly-broken commitments (selected on day 1, completed on day 5 = 4 "misses"), which directly fights Pillar 2's push toward larger, verified tasks. Instead it measures **distinct tasks committed to during the month that reached `completed`** — day-level duplicates (the same task selected on several different days) count as one commitment, not several.
- **`lib/performance/composite.ts`** — pure, DB-free scoring core: `computeComposite()` (weighted blend + renormalisation), and unit converters (`relativeToBest`, `ratingToScore`, `ratioToScore`, `attendanceToScore`) that turn raw units into the shared 0–100 scale. **`lib/performance/monthly-score.ts`** — the DB half: `gatherMonthlyInputs()` fetches every input org-wide in 6 queries (not 6×N per department), `scoreEmployee()` turns one employee's raw inputs into a `CompositeResult` (Tech output = points relative to the department's top scorer that period; Sales/BD output = metric attainment, already an absolute 0–100 measure).
- **Schema (migration `20260808180000_add_recognition_components`, purely additive):** `recognition_snapshots.components jsonb NULL` — the full breakdown that produced a monthly score, kept alongside it so a rank stays explainable after the fact even as later data changes it. Null on weekly rows and pre-Pillar-6 data.
- **Cron.** `lib/cron/recognition.ts`'s `computeAndReplace()` branches on period type: `monthly` calls `gatherMonthlyInputs` + `scoreEmployee` per department (still keyed to the department's top scorer, same idempotent delete+recreate transaction as before); `weekly` is byte-for-byte the original logic.
- **API.** `GET /recognition` — each `monthly` row now includes `components` (null on weekly / pre-Pillar-6 rows); `recompute` and `publish` are unchanged and still work on top of composite snapshots (publish re-flags `is_employee_of_month` on whatever the latest snapshot looks like, same as before).
- **UI.** `components/recognition/score-breakdown.tsx` — collapsible per-component breakdown (bar + weight% + raw detail string + one-line description), with an explanatory note listing anything renormalised away for lack of data. `recognition-screen.tsx` — each leaderboard row's score is now a toggle that expands the breakdown inline; weekly rows render as a bare score with no toggle (nothing to expand). ### Phase 12 — Forgot/reset password (2026-07-16, on `main`)

- **Flow:** `POST /api/v1/auth/forgot-password` (`{ email }`, public) always returns the same generic response regardless of whether the account exists — no enumeration signal. If it does exist: any previous unused token for that user is invalidated, a random 32-byte token is generated, its **sha256 hash** (never the raw token) is stored in a new `PasswordResetToken` row with a **15-minute expiry**, and an email is sent via Brevo with a link to `/reset-password?token=...`. `POST /api/v1/auth/reset-password` (`{ token, new_password }`, public) validates the token (unused + unexpired), enforces the existing `checkPasswordStrength` policy, and — matching change-password's precedent — **bumps `tokenVersion`** (revokes every outstanding session) and marks the token used; it does **not** auto-login, the user returns to `/login`.
